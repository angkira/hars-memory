## 0. TL;DR

- Framework: **Textual** (MIT, 8.2.8 released 2026-06-30 per PyPI JSON; Python >=3.9; deps rich/pygments/markdown-it, no
  native build). Async-native, so SSE + HTTP polling fit without threads. First-party headless test harness (`App.run_test()` /
  `Pilot`) plus `pytest-textual-snapshot` (MIT, 1.1.0, last released Jan 2025: stable, low-churn, but slowish upstream).
  Alternatives rejected in section 1.
- Architecture: **the TUI is a pure out-of-process client**. No `import hars_memory.mcp_server` in the TUI process. It talks to
  (a) the trace listener `:8098` (SSE recall + `/healthz /stats /graph /coords`), (b) the MCP streamable-HTTP endpoint `:8099`
  for tool calls (writes, session tools, status), (c) the index-job REST service, and (d) read-only local files for things with
  no API yet (session dirs, eval `runs/`, `batch_state.json`). Reasons in section 2.
- MVP (Phase 1, ~4-5 dev days): Health, Recall-with-trace, Session browser (list + detail + graph tree), Eval results viewer.
  Everything else is later and some of it should never be built (section 8).
- Real API gaps (section 4): no job list / job progress, no session-graph read API (entities/relations/compactions), no unified
  health for embedder/extractor/Qdrant, no eval-run launcher API (and it should stay a subprocess), `index-batch` and
  `migrate-index` are CLI-only with no machine-readable progress.
- The eval launcher is the riskiest module because `run_longsession.py` and `.plans/2026-10-26_long-session-eval.md` DO NOT EXIST
  yet; only `run_chainreplay.py` (3.4k lines) and `run_longreplay.py` (593 lines) do. Design against a thin "run adapter"
  and build the viewer first; the launcher last.

## 2. Architecture: HTTP/MCP client vs in-process

Recommendation: **out-of-process client, three thin adapters, one local-files adapter.** In-process is rejected because:

1. `hars_memory.mcp_server` (6667 lines) imports LightRAG/torch/sentence-transformers at module scope and holds `_rag_instance`
   and the project registry caches in module globals (CLAUDE.md: "The MCP process is long-lived"). A TUI that imports it would
   load a second embedder + index copy (hundreds of MB, plus iGPU contention) and show state that is not the live service's.
2. Cache invalidation: the TUI process would not see `memory_remember`/`consolidate` effects without its own invalidation.
   The live service owns correctness.
3. Remote use: owner runs the service on `memory-host` (WireGuard, `HARS_MEMORY_MCP_BIND_HOST`); a TUI that works over the
   same endpoints as agents works from a laptop too.
4. Auth: going through MCP uses the same `access_token`/OAuth permission map (mcp_server.py:5058-5071) as agents; in-process
   would bypass it.

Adapters (all in `hars_memory/tui/clients/`, each independently unit-testable without Textual):

| Adapter | Transport | Used for |
|---|---|---|
| `TraceClient` | httpx SSE + GET to trace listener (`trace.py:544 trace_config_from_env`, default `:8098`) | recall trace stream, `/healthz`, `/stats`, `/graph`, `/coords` |
| `McpClient` | `mcp` package streamable-HTTP client to `:8099/mcp` (http_server.py module docstring; `mcp>=1.0,<2` already pinned, CLAUDE.md) | every `memory_*` tool call: remember, compact, merge, session_status, entities, related, inspect, sync_status, consolidate, list_projects, status |
| `JobsClient` | wraps existing `HarsMemoryClient` (sdk.py:99) run in `asyncio.to_thread` | index-job service create/extend/poll/cancel/versions |
| `LocalFs` | read-only filesystem | session dirs (`HARS_MEMORY_SESSIONS_DIR`), eval `runs/*`, `batch_state.json`, `/mnt/datasets/ft/artifacts/*` |

Config: `~/.config/hars-memory/tui.toml` (profiles: name, mcp_url, trace_url, jobs_url, token env-var NAME, sessions_dir,
eval_root, artifacts_root). Tokens are read from env at call time, never written to the file or logged (matches AGENTS.md
credential model). Profile switcher in the header (home box vs remote).

Fallback when a service is down: each adapter returns a typed `Unavailable(reason)` and the screen shows it; the app never
crashes on a dead endpoint. This is the same philosophy as `preflight_verdict` (run_chainreplay.py:1897).

Write safety: every mutating action (remember, compact, merge, consolidate, forget, delete) goes through a confirm modal that
prints project + tool + args; admin-class tools (`forget`, `delete_document`, `consolidate`; mcp_server.py:5069-5071) are
hidden unless `--allow-admin` or profile flag. Per CLAUDE.md, writes into project `default` (the shared SRE KB) require an
explicit second confirmation; this is a product rule, not just a nicety.

## 3. Screens and data sources

Legend: OK = existing API usable; GAP-n = see section 4.

### 3.1 Health (MVP)
Panels: HARS MCP/API, trace listener, embedder, extractor/query LLM, Qdrant, index-job service, engine router shards.
- HARS API: `GET /healthz` on the HTTPS server -> `_health_payload` (http_server.py:355-380: status, mode, uptime, index_warm,
  warmup_seconds, oauth, engine_router). OK.
- Trace listener: `GET :8098/healthz` (trace.py request handler, `path in ("/healthz", "/graph-stats/healthz")`). OK.
- Engine shards: `engine_router.engines` from the same payload; `EngineRouter.stats()` (mcp_engine.py:509), refresh
  `probe_health` (mcp_engine.py:526). OK.
- Index/Qdrant: MCP `memory_status` -> `_index_status` (mcp_server.py:1001; Qdrant branch ~1049-1110 does a 3 s
  `QdrantClient` collection lookup, so Qdrant reachability + vector counts are already there). Partially OK; Qdrant is only
  visible when the vector backend is qdrant, and errors come back as strings in `vector_info`. GAP-3.
- Embedder: no endpoint. `server/embedder.py` supports `HARS_MEMORY_EMBED_PROVIDER=http` (shared embedder process) but nothing
  exposes its health. TUI can probe the configured URL itself (a GET to the embedder base URL from profile config). GAP-3.
- Extractor/query LLM: no endpoint; same story (`HARS_MEMORY_LLM_*`). Cheap probe = `GET {base}/models` from the profile. GAP-3.
- Index job service: `GET /health` / `/healthz` (service/api.py:143-144). OK.
Refresh: 5 s polling worker, red/amber/green row per service with last-latency and last-error. Do not auto-refresh faster.

### 3.2 Recall with trace (MVP)
Input: question, project, mode, top_k, ll_keywords, hl_keywords (per CLAUDE.md the keyword fields matter and should be prominent;
default language hint "English for the SRE KB"). Output, rendered progressively as SSE events arrive:
`trace_start -> bm25_hits -> vector_hits -> fusion -> rerank -> graph_expand -> context -> result -> done|error`
(`.plans/2026-10-17_live-recall-trace-sse.md`, `trace.py:177 stream_recall_events`). Each stage = one collapsible panel with
per-channel latency (`t_ms`, `seq`), hit table (doc/section/file/score), rerank before/after and skip reason. Final `result`
event holds the unchanged `memory_recall` JSON; show `hybrid.rerank {backend, applied, fallback_reason}` (AGENTS.md) and
`routing` when present. Actions on a hit: open file at `start_line` in `$EDITOR`/pager (CLAUDE.md: "open the cited file at
start_line"), copy chunk id.
- Request args: `trace.py:351 _recall_args` honours only question, mode, top_k, context_only, project, fetch_top_k,
  ll/hl_keywords, access_token. It does NOT accept `session_id`, `view`, `debug`, or `session_graph` (the opt-in session-graph
  recall just added, commit 1df090d). GAP-1: session recall cannot be traced over SSE; fall back to MCP `memory_recall` (no
  stage events) for session questions.
- History: ring buffer of last N queries kept in the TUI's own state file (not in the KB).

### 3.6 Indexing / re-indexing / migration jobs (Phase 3)
Three disjoint mechanisms, none with a common progress model:
1. HTTP index-job service: `POST /v1/index-jobs` (service/api.py:148), `GET /v1/index-jobs/{id}` (282), `POST .../cancel` (289),
   `GET /v1/indexes/{id}/latest` (326), `/versions/{n}` (332), `/artifact` (340); SDK `HarsMemoryClient` (sdk.py:99-237).
   Status enum queued/running/succeeded/failed/cancelled (service/models.py:34). **GAP-4**: no list-jobs endpoint, no progress
   fraction (`JobInfo` has only status/error/version, sdk.py:45); TUI can only poll known ids. Needs `GET /v1/index-jobs?limit=`
   and a `progress` field; until then the screen shows jobs created from this TUI (ids remembered locally) plus a "paste job id".
2. `memory index-batch` (collect/submit/status/apply/run/cancel/compare, cli.py ~1294): state in `<index>/batch_state.json`
   with per-part done/total, `last_progress_at`, STALLED/CANCELLING/ABANDONED, cost guard exit code 3, timeout exit 4
   (AGENTS.md). TUI reads `batch_state.json` directly (read-only) for progress and shells out to the CLI to start/cancel.
   Estimate = `memory index-batch collect --dry-run` (prints estimate, writes nothing). GAP-6 (file schema is undocumented as
   an API; pin it with a test, section 6).
3. `memory migrate-index` (cli.py:1254; `ingest/migrate.py`, plan 2026-10-01): CLI subprocess only; no progress file. Show
   stdout tail. GAP-6.
Also `memory consolidate` (cli.py:1220) and MCP `memory_consolidate` (admin). Note the live index is refused by index-batch by
design (AGENTS.md); the TUI must not offer a path around it.
Job runner pattern: the TUI spawns the CLI via `asyncio.create_subprocess_exec`, tees stdout/stderr into
`/mnt/datasets/ft/artifacts/<ts>-<name>/run.log` (CLAUDE.md run-artifact rule applies to indexing applies), and records the
exact command line. A TUI-launched job must survive TUI exit (`start_new_session=True`, state in the artifact dir) and be
re-attachable on next start.

### 3.8 NeuroCompact eval module (Phase 2 viewer, Phase 4 launcher)
All sources are files under `experiments/neurocompact-eval/` (configurable `eval_root`); there is no service.

Datasets (read-only):
- `chains.jsonl` (10 chains x 70 items), `dataset_stats.md`, `verify_chains.report.md`, `longreplay/longreplay-manifest.json`

  (`make_chains.py`, `make_longreplay_dataset.py`, `import_opencode.py`, `import_openhands.py`) are NOT wrapped: they are
  one-shot, cost money, and are done.

Run launcher (Phase 4; see risk R3):
- Real entry points today: `scripts/run_chainreplay.py` flags: `--chains --arms --limit --dry-run --out --provider --agent-model
  --judge-model --mem-budget --mem-budgets --require-no-clip --preflight-session --calibrate --sweep-caps ...`
  (run_chainreplay.py:3181-3270); `scripts/run_longreplay.py` (`--model --arms --limit --dry-run`, run_longreplay.py:387-398).
  The `run_longsession.py` described by the 2026-10-26 long-session plan does not exist: `ls .plans` has no
  `*long-session*` file and no such script. The launcher must be a **form generated from a declarative runner descriptor**
  (`runners.toml`: script path, flag name/type/default/choices/help), not hard-coded to run_chainreplay's argparse, so
  `run_longsession.py` plugs in later by adding a descriptor. Parsing `--help` is fragile; hand-written descriptors for the two
  existing scripts, validated by a test that diffs descriptor flags against `argparse` introspection (import the script's
  `build_parser`, which does not exist yet: current `main()` builds the parser inline, run_chainreplay.py:3181; needs a tiny
  refactor in experiments/ or the test shells out to `--help` and compares flag names). GAP-7.
- Dry-run/preflight: `--dry-run` prints the exact per-arm env and a cost projection with no API calls
  (run_chainreplay.py ~290 "Projection constants for --dry-run", ~1391 "Exact env per arm"); live preflight is one
  `memory_recall` before any spend (`preflight_verdict`, run_chainreplay.py:1897; `--preflight-session`). Launcher flow:
  Configure -> **Dry-run (always first, mandatory)** -> show projection + family-conflict check result
  (`family_conflict`, run_chainreplay.py ~3290: agent/judge model families must differ; runner exits 2) -> confirm with typed
  cost cap -> Launch. The TUI must refuse to launch live if the last dry-run for identical args did not exit 0.
- Output dir: the runner refuses a non-empty `--out` (HANDOFF) and pins it absolute; the TUI generates
  `/mnt/datasets/ft/artifacts/<UTC-ts>-<name>/` per CLAUDE.md and passes it as `--out`, so a TUI run is automatically a
  conformant artifact dir. Today runner writes `records.jsonl`, `compactions.jsonl`, `chain_budget.jsonl`, `run_budget.json`
  (run_chainreplay.py:3415-3445,3726), NOT the CLAUDE.md-mandated `samples.jsonl/summary.json/run.log/MANIFEST.json`.
  GAP-8: the TUI wrapper writes `run.log`, `MANIFEST.json` (command line, machine, start/end, models) and symlinks/copies
  `inputs/`+`scripts/`; mapping records.jsonl -> samples.jsonl is a rename-by-reference, decide with owner (see Open questions).
- Live progress: no machine-readable progress channel. Per-chain rows are written once at chain end
  (HANDOFF: "rows buffered per chain and written once at chain end"), so progress granularity = chains completed, from
  tailing `records.jsonl`/`chain_budget.jsonl` plus the runner's stdout (`RUN BUDGET`, `[budget warn]`, `RECALL FAIL`,
  `CLIP FAIL` lines). TUI shows: chains done/total, per-arm validity, running warnings, stdout tail. Anything finer needs the
  runner to emit JSONL events (GAP-8; a 30-line `--events-jsonl` addition, separate PR in experiments/).
- Cost tracking: records carry `usage.input/output` (run_chainreplay.py ~1312 `ex["usage"]`) and keyword cost
  (`keyword_cost_usd`, ~1847); no consolidated spend counter. TUI sums per-record usage x price table (profile config;
  OpenRouter balance snapshot like `runs/full-spend.txt`, RUNBOOK-gate.md:143, is manual today). Show "estimated, not billed".
  Hard cap enforcement must live in the runner (it has none for chain runs as far as read: only `index-batch` has
  `--max-cost`); TUI "kill at cap" = SIGTERM to the process group, best effort. GAP-8.
- Stop: SIGINT to the subprocess group, then show which chains were written (valid flag per chain).

Results / metrics viewer (MVP):
- Inputs: `runs/<run>/records.jsonl`, `judged.jsonl`, `judge-input.jsonl`, `run_budget.json`, `chain_budget.jsonl`,
  and the summary JSON written by `metrics_v2.py --json` (metrics_v2.py:1177,1282-1288: `{"meta", ...}`), plus gate files in

Artifact browser:

## 8. What is NOT worth putting in a TUI (be critical)

1. **Graph visualisation of the main KB** (thousands of nodes). A character grid cannot show a force layout; the cosmos view
   already exists as the web "Memory Travel" UI (`/graph`, `/coords`). TUI: counts, top-degree nodes, neighbour tree, "open in
   browser" link. Session graphs (tens of nodes) as an indented tree only; no ASCII node-link drawing.
2. **Embedding-space/UMAP coords, heatmaps, bootstrap CI plots.** Show numbers and a 1-line Sparkline at most; render real
   plots with a notebook/HTML. Terminal CIs as `[lo, hi]` text are enough.
3. **Project CRUD, auth/token/key management** (`memory auth ...`, cli.py:1383). Security-sensitive, rarely used, already a
   clean CLI; wrapping it in a TUI adds attack surface and no speed-up.
4. **Dataset generation/editing/import** (`make_chains.py`, `import_opencode.py`, `import_openhands.py`, QA gen). One-shot,
   paid, already run, frozen protocol. Viewer yes, wrappers no.
5. **Re-implementing metrics/judging** in the TUI (section 3.8). A second implementation of a pre-registered protocol is a
   correctness hazard. View and shell out only.
6. **Free-form `memory_forget`/`delete_document`/`consolidate` buttons enabled by default.** Admin tools stay behind a flag and
   typed confirmation; a stray keypress in a TUI is too cheap compared with a CLI command you must type.
7. **Embedding a general log/metrics dashboard** (GPU, CPU, systemd). That is btop/journalctl territory; the Health screen shows
   only service reachability and the numbers HARS itself reports.
8. **A TUI "agent chat" / pi session driver** for the eval. The runners drive `pi` themselves; the TUI launches the runner,
   not the agent.
9. **Editing files** (documents, `.env`, strategies YAML). Open in `$EDITOR`; do not build a text editor widget.
10. **Cross-run statistical comparison UI** beyond a side-by-side of two `metrics_v2` JSONs. Pre-registered analysis exists in
    one place (REPORT-PROTOCOL.md).

## 9. Risks

| # | Risk | Likelihood / impact | Mitigation |
|---|---|---|---|
| R1 | Textual major-version churn (8.x already; snapshots break across minors) | M / M | pin `<9`, few snapshots, adapters independent of Textual, wrap widgets behind our own small component layer |
| R2 | `run_longsession.py` and its plan don't exist; runner flags/outputs will change under the launcher | H / M | descriptor-based launcher built last (Phase 4), viewer reads only stable files; revisit when the plan lands |
| R3 | A TUI "Launch" button makes it too easy to burn money or invalidate a frozen-protocol run (runs are paid, OpenRouter balance was $6.52 before the full run, RUNBOOK-gate.md:143) | M / H | mandatory dry-run gate, typed cost cap, family-conflict check surfaced, refuse non-empty out dir, never offer protocol-affecting flags (`--allow-degraded`, `--no-require-no-clip`) without an explicit "protocol deviation" toggle that is written into MANIFEST |
| R4 | LocalFs interim reads of session dirs race with writers (kv/graphml mid-write) | M / L | read-only, retry-on-parse-error, rely on `_write_json_atomic` (session_memory.py:216) for JSON; graphml read tolerates failure (fail-soft like `_graph_counts`) |
